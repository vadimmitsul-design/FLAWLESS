# Архитектура FLAWLESS

FLAWLESS предоставляет веб-кабинет, OpenAI-совместимый API и Telegram-бота.
Приложение использует FastAPI, SQLAlchemy AsyncSession, PostgreSQL и LiteLLM.
Внутренний и клиентский экземпляры используют один исходный код, отдельные
базы, настройки, порты и compose-проекты. Продуктовые различия задаются
настройками, в том числе флагами доступности разделов.

## Границы модулей

- `app/main.py` собирает приложение, middleware, роутеры и lifespan.
- `app/api/` содержит HTTP-адаптеры: зависимости доступа, валидацию входа,
  HTTP-ответы, перенаправления и шаблоны страниц.
- `app/services/` выполняет прикладные сценарии и запросы для представлений.
  Сервис не импортирует роутер или `app.main`.
- `app/services/billing.py` содержит денежные правила и операции над кошельком;
  `pricing.py` и `dlp.py` отвечают за цену и обработку секретов.
- `app/integrations/` содержит адаптеры LiteLLM и Telegram;
  `app/schemas/` описывает входы и выходы API.
- `app/core/` содержит независимые доменные ошибки и инфраструктуру HTTP:
  lifespan, middleware, форматирование и создание окружения шаблонов.
  Окружение шаблонов принадлежит `app.state.templates`.
- `app/db/models.py` описывает схему, `app/db/session.py` создаёт движок и сессии.
  Повторяющиеся критичные запросы вынесены в `app/db/repositories/`.
  Миграции схемы принадлежат Alembic в `alembic/versions/`.
- `app/workers/` содержит уборку зависших резервов и операционные оповещения.
- `app/templates/` содержит представления, включая встроенные CSS и JavaScript.

Новый запрос не требует отдельного репозитория только ради обёртки над
`select()`. Выделять общую функцию стоит для повторяющегося запроса или
самостоятельного правила, которое нужно проверять отдельно.

Сервисы ресурсов принимают типизированные данные, выполняют проверки и
`flush()`, а HTTP-адаптер фиксирует операцию одним `commit()`. Существующие
денежные операции сохраняют явные границы резервирования и финализации;
их нельзя механически убрать, пока вызывающий сценарий не принял владение
транзакцией. Общий цикл вызова модели находится в `app/services/chat.py`.

## Денежный сценарий

1. Проверить доступ, модель, сообщения и действующую цену.
2. Заблокировать кошелёк плательщика, проверить лимиты и доступный остаток.
3. Создать событие `pending` с резервом и зафиксировать его отдельной
   транзакцией. Параллельный запрос должен увидеть резерв до вызова модели.
4. Вызвать провайдера без удержания блокировки кошелька.
5. При финализации проверить актуальный статус события под блокировкой.
   Повторная финализация не должна повторять списание.
6. Согласованные изменения баланса, журнала, стоимости промпта, роялти и
   сохранённого ответа фиксировать вместе. При ошибке освобождать резерв
   через тот же денежный слой.

Доступный остаток равен `balance_rub − SUM(reserved_rub)` для `pending`
событий. Резерв не является списанием и не создаёт запись журнала.
`customer_id` обозначает пользователя, `billing_customer_id` — плательщика;
для детского аккаунта это разные люди.

`WalletLedger` — append-only журнал. Исправления оформляются компенсирующими
записями, а не переписыванием истории. Денежные величины считают через
`Decimal`; баланс и журнал хранят четыре знака после запятой. Событие
фиксирует применённую цену, курс и наценку, чтобы последующая смена тарифов
не переписала уже выполненную операцию.

Для нескольких кошельков порядок блокировок должен быть единым. Нельзя
удерживать блокировку плательщика, а затем произвольно блокировать автора:
два встречных платежа могут образовать взаимную блокировку.

## Различия каналов

HTTP, Telegram и веб-чат используют общие правила подготовки и учёта
платного вызова. Адаптеры сохраняют особенности своего контракта: API
принимает tool calls и ключ идемпотентности, потоковый API отдаёт SSE,
веб-чат сохраняет диалог, Telegram поддерживает сообщения и голосовой вход.

Fallback допустим до отправки первого потокового ответа клиенту. После
начала выдачи нельзя незаметно заменить модель и повторить уже полученный
контент. Отмена задачи, обрыв клиента и остановка процесса требуют разных
путей завершения, но используют общую защиту финализации от повторов.

## Фоновое обслуживание

Lifespan запускает уборщик и, если настроен токен, Telegram polling.
Остановка приложения отменяет и дожидается этих задач. Уборщик закрывает
старые `pending` события без списания неподтверждённой стоимости. Отключать
его нельзя: после аварийного завершения процесса Python `finally` не
исполняется и резерв останется занят.

При отмене обычного нестримингового запроса до начала финализации резерв
также может сохраняться до прохода reaper. Внешний вызов провайдера не является
частью транзакции PostgreSQL; откат БД не отменяет уже выполненную моделью работу.

В том же цикле выполняется сверка кошельков. Один SQL-запрос сопоставляет
`Customer.balance_rub` и сумму `WalletLedger.delta_rub`, включая клиентов
без записей журнала. Несовпадение попадает в лог и настроенный канал
оповещений. Сверка не меняет деньги: оператор расследует причину и при
необходимости проводит компенсирующую операцию.

Rate limit и подавление повторных оповещений хранятся в памяти процесса.
Лимитер представлен явными экземплярами `RateLimiter`, имеющими отдельные
счётчики для обычных запросов и входа по паролю. `AlertCooldown` отдельно
управляет интервалом повторного оповещения; его можно передать рабочей
функции явно. Ошибки отправки в Telegram проходят через удаление токена
из текста ошибки до записи в лог.
Текущий compose запускает один процесс приложения. Перед добавлением
workers/реплик нужно спроектировать общий лимитер, координацию фоновых
работ и единственного Telegram poller на токен. Разным экземплярам нельзя
передавать один Telegram-токен.

## Проверка изменений

Денежные изменения проверяют на PostgreSQL с миграциями Alembic, включая
конкурентные запросы через отдельные соединения. SQLite не воспроизводит
`SELECT FOR UPDATE` и не подтверждает отсутствие гонок. В тестах провайдер
моделей и Telegram заменяются заглушками; реальные платные вызовы не нужны.

HTTP-контракты, права доступа, флаги разделов, идемпотентность, SSE и
поведение обрыва соединения проверяются независимо от физического
расположения функций. Перенос модуля сам по себе не является основанием
менять ожидаемое поведение теста.

Воспроизводимое окружение, команды проверок и точная область type check
описаны в [TESTING.md](TESTING.md). Быстрый исторический HTTP-набор пока
использует общую SQLite-базу на прогон; PostgreSQL-набор изолирован в
`integration_tests/`, поднимает схему миграциями и проверяет реальные гонки.
